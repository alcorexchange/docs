title: "Bridge"

The Alcor bridge moves tokens between Ethereum, BNB Smart Chain, Polygon, Telos,
WAX, XPR Network, Vaulta, Sui, NEAR, TON and Solana. Telos is the hub: every route runs
between Telos and one other chain, and a transfer between two other chains
passes through Telos on its own — the user signs once.

There are five ways to bring it into your project:

| Way | Best when | Your code |
| --- | --- | --- |
| **[Deposit addresses](#deposit-addresses)** | Your users fund an account or [pay you](#payments-and-processing) from other chains, often straight from an exchange | One API call per user or order |
| **[Deposit link](#deposit-link)** | You send users to the Alcor bridge page with the transfer filled in | None |
| **[Deposit widget](#deposit-widget)** | The bridge opens over your own page | A script tag |
| **[Bridge API](#bridge-api)** | You show routes, limits and transfer status yourself | HTTP reads |
| **[Bridge contracts](#bridge-contracts)** | A bot, wallet or exchange signs the transactions itself | Contract calls |
| **[Light clients](/developers-api/light-clients)** | Your own contract checks what happened on another chain: a message, a lock, a vote | Table reads and merkle proofs |

<Callout type="info">

This page explains each way. The complete reference — every endpoint and field, every chain's transaction, written to be handed to a developer or an AI agent — is served by the bridge itself: <a href="https://telos.alcor.exchange/api/bridge/docs">/docs</a> (the API), <a href="https://telos.alcor.exchange/api/bridge/docs/bot">/docs/bot</a> (signing on every chain) and <a href="https://telos.alcor.exchange/api/bridge/openapi.yaml">/openapi.yaml</a>.

</Callout>

Supported assets: USDC, USDT, ETH, BNB, POL, WAX, XPR, A (Vaulta), EASY, SUI,
NEAR, GRAM (TON) and SOL. Which pairs are open right now, with minimums and maximums,
is always [Routes](#bridge-api).

## Deposit addresses

Each of your users gets an address of their own. Whatever they send there —
from a wallet or straight from an exchange, the native coin included — reaches
the account you named on Telos, WAX, XPR Network or Vaulta. The user needs no
wallet connection, no signature and no gas. The address is permanent and works
again and again.

No API key, no sign-up, no bridge fee. The API is open to any origin (CORS `*`),
so a page can call it straight from the user's browser.

```text
user sends USDC on BNB Smart Chain to their address
  → forwarded into the bridge (≈15 s)        ← the gas, out of the deposit, at most 1%
  → Telos (≈30 s)
  → paid out on WAX to your account, with your memo (≈2 min)
```

The whole integration is three steps:

1. **Get the user's addresses**: one request, the same answer every time.
2. **Credit the user** when the payout reaches your account on chain. That transfer, with your memo, is the signal: there is no webhook to wait for.
3. **Show progress** in your page, if you want to: what the bridge sees at the address, then the crossing, pushed as server-sent events.

### 1. Get the addresses

```shell
curl -X POST https://telos.alcor.exchange/api/bridge/v1/deposit-addresses \
  -H 'content-type: application/json' \
  -d '{ "chain": "wax", "to": "yourproject", "memo": "user-42" }'
```

| Field | Description |
| --- | --- |
| chain | Where it is paid out: `telos`, `wax`, `xpr` or `vaulta` |
| to | The account paid. It must exist |
| memo | Optional. The memo every payout carries, so one account of yours tells its users apart: put your user's id here. 1–64 characters of `A-Z a-z 0-9 . _ - :`. Another memo is another address |

The answer, trimmed:

```json
{
  "address": "0xb4b257e395f84f586479548d624302384d65ec58",
  "destination": { "chain": "wax", "to": "yourproject" },
  "chains": [
    { "id": "bsc", "name": "BNB Smart Chain", "chainId": 56,
      "tokens": [ { "symbol": "USDT", "token": "0x55d3…7955", "decimals": 18,
                    "min": "5000000000000000000", "max": "15449853123000000000000",
                    "least": "5050505050505050506" } ] }
  ],
  "ton":    { "address": "UQ…", "rawAddress": "0:…", "tokens": [ … ] },
  "near":   { "address": "<40 hex>.dep.alcorexchange.near", "ready": true, "tokens": [ … ] },
  "sui":    { "address": "0x<64 hex>", "tokens": [ … ] },
  "solana": { "address": "<base58>", "tokens": [ … ] },
  "feeCap": "1%"
}
```

* `address` — the user's address on **Ethereum, BNB Smart Chain and Polygon**: one address on all three, listed in `chains`.
* `ton.address`, `near.address`, `sui.address`, `solana.address` — their addresses on **TON, NEAR, Sui and Solana**, each its own. Show the NEAR one only while `near.ready` is true.
* `tokens`, per network: what the address takes. Show only these. Amounts are raw units of that token (divide by `10^decimals`). **`least` is the minimum to show**: what to send so that it is forwarded now, with room for the gas. It moves with gas prices; read it again when you show the address. `max` is null where there is no limit.

**Call it whenever you show the address.** It answers the same addresses for the
same request, so you do not have to store them, though you may.

**Limit:** 20 new addresses an hour from one client, 2000 a day in all
(`429 RATE_LIMITED`). An address asked for before always answers. Call it from
the user's browser and each user has their own allowance. If you register from
your server for many users, ask us to raise it for your server.

`400 INVALID_REQUEST` means a deposit would only come back: no such account,
a bad memo. Show the message.

### Show it to the user

* The address, a copy button and a QR of the **plain** address (exchanges scan plain addresses).
* The networks it works on, by name, and plainly: **sending on any other network (Arbitrum, Base, Tron…) may lose the money.**
* Per network, the tokens and `least` as the minimum. Less waits at the address until more arrives.
* "You can withdraw straight from an exchange to this address." Bybit refuses to send to the Solana and NEAR addresses; KuCoin and Binance send.
* On Solana, USDC and USDT go to the address's token account. Phantom and exchanges create it themselves.

### 2. Credit the user

The payout is an ordinary token transfer to your account. On your chain it is
final, and it is the one thing to credit on.

| Chain | The payout |
| --- | --- |
| WAX, XPR, Vaulta | A `transfer` from `bridge.alcor` with the memo exactly as you set it. Token contract: `wrap.alcor` for USDC, USDT, ETH, BNB, POL, SOL; the chain's own for its coin (`eosio.token`, `core.vaulta`) |
| Telos | A `transfer` from `bridge.alcor` of a `wrap.alcor` token, memo `<your memo>\|<network>:<deposit address>`. Read your memo up to the first `\|` |

Watch your account's incoming transfers the way you already do for direct
deposits: a contract's `on_notify`, or your history reader. Find the user by
the memo. The amount is what arrived, after the forward's gas.

<Callout type="warn">

If <code>to</code> is a contract: check that the transfer's first receiver is the token contract you expect and that it comes from <code>bridge.alcor</code>, since anyone can notify you of a fake token. And never fail our transfer: a refused payout goes back to the deposit address and waits there for support. Accept it and settle with your user your own way.

</Callout>

### 3. Show progress

A deposit goes through two stages, and the API has a stream for each. Both are
[server-sent events](https://developer.mozilla.org/docs/Web/API/Server-sent_events):
the browser's `EventSource` reconnects by itself.

| Stage | What the user sees | Stream | Poll instead |
| --- | --- | --- | --- |
| At the address, not forwarded yet | "Received, forwarding…" | `GET /v1/deposit-addresses/<address>/stream` | `GET /v1/deposit-addresses/<address>` |
| In the bridge, from the forward to the payout | A stage, a progress bar, "arrived" | `GET /v1/stream?party=<address>` | `GET /v1/activity?party=<address>` |

```javascript
const API = 'https://telos.alcor.exchange/api/bridge/v1'

// The user's addresses
const a = await (await fetch(`${API}/deposit-addresses`, {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ chain: 'wax', to: 'yourproject', memo: 'user-42' }),
})).json()
const addresses = [a.address, a.ton?.address, a.near?.address, a.sui?.address, a.solana?.address].filter(Boolean)

// Stage 1: money at the address, on any of its networks
const atAddress = new EventSource(`${API}/deposit-addresses/${a.address}/stream`)
atAddress.addEventListener('status', (e) => {
  const { pending, held } = JSON.parse(e.data)
  showWaiting(pending)            // [] when nothing waits
  if (Object.keys(held).length) showContactSupport()
})

// Stage 2: the crossing, from the forward to the payout
const parties = addresses.map((p) => `party=${encodeURIComponent(p)}`).join('&')
const crossing = new EventSource(`${API}/stream?${parties}`)
crossing.addEventListener('snapshot', (e) => setList(JSON.parse(e.data).transfers))   // replace the list
crossing.addEventListener('transfer', (e) => {
  const { change, transfer } = JSON.parse(e.data)
  upsert(transfer)                // by transfer.key
  if (change === 'delivered') notify(`${transfer.amount} ${transfer.asset.symbol} arrived`)
})
```

**Stage 1: `status`.** Sent on opening and again each time the courier's view
of the address changes. One stream covers all of the address's networks.

* `pending` — what is at the address and not forwarded yet: `[{ chainId, symbol, token, raw, since, reason?, nextTry? }]`. `raw` is in the token's units on that network; `reason` is a sentence saying why it waits (under the minimum, a failed forward retried at `nextTry`); without it, the next pass forwards it.
* `forwards` — the last 20 forwards into the bridge, newest first: `{ chainId, tokens: [{ token, raw, fee }], tx, at }`.
* `held` — what came back and waits for support, keyed `<chainId>:<address>:<token>`. Show "returned, contact support", not an error.

**Stage 2: `snapshot` and `transfer`.** `snapshot` is the list as it stands, on
opening (the newest 50). `transfer` is one change: put it in your list by its
`key`. `change` is one word:

| change | |
| --- | --- |
| `new` | The bridge has just seen it |
| `progress` | A confirmation, a stage, a transaction. Update the bar |
| `delivered` | Paid out to your account |
| `returned` | Not delivered, back at the deposit address |

Each transfer has `stage` (a sentence to show as it is), `percent` (0–100),
`etaAt` (the unix second it should be done, for a countdown), `sent` (what the
user sent) and `amount` (what arrives, after the forward's gas). `party` takes up
to 10 addresses, so the user's addresses on every network fit in one stream. A
dropped connection loses nothing: the events since are sent again on reconnect.

**One stream for all your users.** A backend can follow every deposit to your
account at once: `GET /v1/stream?party=yourproject&role=recipient`. Each
transfer's `from.address` is the deposit address it came through, so you know
whose it is (a TON one is spelled `0x` and the 64 hex digits of `ton.rawAddress`).
Use it for display and alerts; credit on the transfer on your chain. To poll
instead: `GET /v1/events?party=yourproject&change=delivered&after=<last>`.

### What it costs

There is no bridge fee. The only cost is the gas to forward the deposit into the
bridge, taken out of the deposit and **never more than 1%** of it. The payout on
Telos, WAX, XPR and Vaulta is on us. `GET /v1/fees` shows the current forward
cost per network and token. It matters on Ethereum, where gas is dear: that is
why `least` is higher there.

### When something goes wrong

Nothing is ever sent back to the sender: an exchange would not credit it. What
cannot be delivered waits at the deposit address for support, under `held`.

* **Less than `least`**: waits at the address until more arrives.
* **More than `max`**: a token is forwarded in parts; a native coin goes whole and waits on Telos until the limit allows.
* **A token the address does not take**: not forwarded; support can return it.
* **Your contract refuses the payout**: back to the address, `held`.

### Payments and processing

Deposit addresses are a crypto payment processor with nothing to run: no keys on the addresses, nothing to
sweep, no fee but the forward's gas.

* **Top-ups:** one address per user, `memo` = the user's id. The address is permanent: the user pays into it
  again and again.
* **Invoices:** one address per order, `memo` = the order id. Show it at checkout with the price; the order is
  paid when payouts with that memo add up to it. What arrives is a little less than what was sent (the
  forward's gas): decide how close counts as paid.
* **Your contract** as `to`: the payout is a `transfer` from `bridge.alcor`, so the contract sees it in
  `on_notify` and credits the order by the memo.

```cpp
[[eosio::on_notify("*::transfer")]]
void on_transfer(name from, name to, asset quantity, std::string memo) {
   if (to != get_self() || from != "bridge.alcor"_n) return;        // not a payout: ignore, never fail
   if (get_first_receiver() != "wrap.alcor"_n) return;               // a fake token with the same symbol
   if (quantity.symbol != symbol("USDC", 6) && quantity.symbol != symbol("USDT", 6)) return;
   const std::string order = memo.substr(0, memo.find('|'));        // Telos appends |<network>:<address>
   credit(order, quantity);
}
```

Limits to plan for: each network's `least` and `max`, 20 new addresses an hour from one client (ask us to raise
it for your server), and a memo of 1–64 characters. A swapping address takes no memo. The whole flow, with a
compiled contract and an invoice script: [alcor-examples](https://github.com/alcorexchange/alcor-examples).

### Addresses that do more

* **Create an account.** An address whose first deposit creates `<nick>.ac` on Telos for a user with no wallet:
  `{ "chain": "telos", "to": "ac", "leg": "<factory memo>" }`. See [Account factory](/developers-api/account-factory#with-a-deposit-address).
* **Swap on the way.** An address that takes one token and delivers another ("send POL on Polygon, get BNB on
  BSC"), in beta: *An address that swaps* in [/docs](https://telos.alcor.exchange/api/bridge/docs).

Every field, the EVM address computed on your side to check the API's answer,

## Deposit link

```text
https://alcor.exchange/v/wax/bridge?from=ethereum&to=wax&recipient=alice.wam&token=USDC&amount=50&partner=mygame&return_url=https://mygame.io/play
```

A plain URL to the bridge page with the transfer already filled in. No code is
needed on your side.

| Parameter | Example | Description |
| --- | --- | --- |
| from | `ethereum` | Chain to start on. The user can still change it. |
| to | `wax` | Chain the tokens land on. |
| recipient | `alice.wam` | Receiving account or address, prefilled. The user can edit it on this page. |
| token | `USDC` | Asset, by the symbol the bridge lists. |
| amount | `50` | Prefilled amount, in token units. |
| partner | `mygame` | Your id, so the deposits you bring are attributed to you. |
| return_url | `https://mygame.io/play` | Shows a "← Back to mygame.io" link. `https` only (`http` is allowed on `localhost`). |

Chains are `ethereum`, `bsc`, `polygon`, `telos`, `wax`, `xpr`, `vaulta`, `sui`,
`near` and `ton`. All parameters are optional. A malformed value is ignored
rather than guessed at.

## Deposit widget

```javascript
// <script src="https://alcor.exchange/sdk/bridge/v1.js"></script>

document.getElementById('deposit').onclick = function () {
  AlcorBridge.open({
    to: 'wax',
    recipient: 'alice.wam',   // fixed: the user cannot change it
    token: 'USDC',
    amount: '50',
    partner: 'mygame',
    onSent: function (e) { console.log('on its way', e.transactions) },
    onFinished: function (e) {
      if (e.outcome === 'delivered') refreshBalance()
    },
    onClose: function () {},
  })
}
```

```html
<!-- Without the script: embed the widget yourself -->
<iframe src="https://alcor.exchange/embed/bridge?to=wax&recipient=alice.wam&token=USDC&partner=mygame&mode=inline"
        style="width:100%;max-width:480px;height:640px;border:0"></iframe>
```

Load `https://alcor.exchange/sdk/bridge/v1.js` and call one of its functions.
The script is tiny and has no dependencies. The path is versioned: `v1.js`
keeps its options and events for as long as anyone uses it.

### Functions

| Function | Shows | Returns |
| --- | --- | --- |
| `AlcorBridge.open(options)` | Modal over your page | `{ close() }` |
| `AlcorBridge.popup(options)` | Separate window. Call it from a click handler. | `{ close() }`, or `null` if the popup was blocked |
| `AlcorBridge.mount(element, options)` | Inline iframe that grows with its content | `{ destroy() }` |
| `AlcorBridge.url(options)` | Nothing. Returns the widget address for your own iframe or link. | `string` |

Browser extension wallets (MetaMask, Rabby) and WalletConnect work in all modes.
In the popup the user's existing Alcor session and wallet connection carry over.

### Options

| Option | Required | Description |
| --- | --- | --- |
| to | true | Chain the tokens land on, as in the [Deposit link](#deposit-link). Into Telos, WAX, XPR and Vaulta the bridge pays out by itself. Into an EVM chain, Sui, NEAR or TON the last step is a release on that chain, which the widget shows when its turn comes. |
| recipient | false | Receiving account. When given, it is **fixed** in the widget. For WAX, the widget checks that the account exists before anything is signed. |
| from | false | Chain to start on. |
| token | false | Asset symbol, e.g. `USDC`. |
| amount | false | Prefilled amount, in token units. |
| partner | false | Your id, for attribution. |
| origin | false | Where the widget is served from. Defaults to the origin of the script itself. |
| onReady, onSent, onFailed, onFinished, onClose | false | Event callbacks, see below. |

### Events

`onSent` receives:

```json
{
  "direction": "hop",
  "from_chain": "ethereum",
  "to_chain": "wax",
  "token": "USDC",
  "amount": "50",
  "sender": "0x285202c8db763db06ab42e0705104cb7919ef95e",
  "recipient": "alice.wam",
  "partner": "mygame",
  "embed": "iframe",
  "transactions": [
    { "chain": "Ethereum", "label": "Send", "ref": "0x0af8…2917", "url": "https://etherscan.io/tx/0x0af8…2917" }
  ]
}
```

`onFinished` receives:

```json
{
  "key": "d:1:12",
  "outcome": "delivered",
  "token": "USDC",
  "amount": "50",
  "transactions": [ … ]
}
```

| Callback | When | Data |
| --- | --- | --- |
| onReady | The widget has loaded and is prefilled | `{ to, recipient }` |
| onSent | The user signed and the transfer is on its way | Transfer details and the first transaction |
| onFailed | The transfer could not be started, e.g. rejected in the wallet | Transfer details plus `errorCode`, `error` |
| onFinished | The transfer reached its end | `{ key, outcome, token, amount, transactions }` |
| onClose | The user closed the widget | `{}` |

`outcome` is `delivered`, or `returned` if the destination refused the tokens
and they went back. `key` identifies the transfer in
[Transfer status](#transfer-status).

<Callout type="warn">

Credit nothing in your app on <code>onSent</code>. Wait for <code>outcome: "delivered"</code>, or better, check the balance on chain. <code>onFinished</code> only fires while the widget is open. A transfer the user walked away from still completes, and you can follow it with <a href="#transfer-status">Transfer status</a>.

</Callout>

### Messages

If you embed the iframe yourself, listen for `postMessage` events from
`https://alcor.exchange`:

`{ source: "alcor-bridge", version: 1, type, data }`

| Type | Data |
| --- | --- |
| ready, sent, failed, finished, close | Same as the callbacks above |
| resize | `{ height }`, the content height in pixels, so you can size the iframe |

Add `mode=inline` to the widget URL to hide its close button. Everything in the
messages is public on-chain data.

## Bridge API

```text
https://telos.alcor.exchange/api/bridge/v1/
```

Read-only HTTP, no key, open to any origin (CORS `*`). Chains are named by id:
`mainnet` (Ethereum), `bsc`, `polygon`, `telos`, `wax`, `xpr`, `vaulta`, `sui`,
`near`, `ton`, `solana`. Amounts are integers in the token's smallest unit: divide by
`10^precision`. Every field of every answer is in
[/docs](https://telos.alcor.exchange/api/bridge/docs).

| Endpoint | What it answers |
| --- | --- |
| `GET /v1/routes` | Every pair of chains each asset can travel between now: `open`, `min`, `max`, and `how` to start it |
| `GET /v1/chains` | Each chain: contracts, limits, whether each direction is open, and `timing` — how long a transfer takes, measured on recent ones |
| `GET /v1/hops/<key>`, `GET /v1/hops?party=…` | A transfer between two chains through Telos, as one journey |
| `GET /v1/transfers/<key>`, `GET /v1/transfers?party=…` | Each leg on its own |
| `GET /v1/stream?party=…` | The same as events, pushed as they happen (server-sent events) |
| `GET /v1/swap/plan` | Any token on one chain to any token on another, swaps included, ready to sign |
| `GET /v1/fees` | What a deposit address forward and a delivered withdrawal cost now |

### Transfer status

```shell
curl https://telos.alcor.exchange/api/bridge/v1/hops/d:1:12
curl "https://telos.alcor.exchange/api/bridge/v1/hops?party=alice.wam"
```

```json
{
  "key": "d:1:12",
  "status": "delivered",
  "progress": { "stage": "Arrived on WAX", "percent": 100, "etaSeconds": null },
  "from": { "chain": "mainnet", "address": "0x285202c8db763db06ab42e0705104cb7919ef95e" },
  "to": { "chain": "wax", "recipient": "alice.wam" },
  "back": { "chain": "mainnet", "recipient": "0x285202c8db763db06ab42e0705104cb7919ef95e" },
  "memo": null,
  "deposit": { "symbol": "USDC", "amount": "50000000", "precision": 6, "src_tx": "0x0af8…2917" }
}
```

A transfer between two chains by its key (the `key` from the widget's
`onFinished`), or every one an account or address took part in, newest first.
`progress.stage` is a sentence to show as it is.

| Status | Meaning |
| --- | --- |
| arriving | On its way to Telos |
| sending | Passed through Telos, on its way to the destination |
| delivered | Paid out to the recipient |
| bounced | Refused on the way, sent back |
| returning | Coming back to the sender |
| returned | Back with the sender |

## Bridge contracts

Everything the page and the widget do is a public contract call. Bots, wallets
and exchanges can make the same calls themselves: no API key, no allowlist, no
Alcor page involved. The guide with every chain's transaction, written for a
bot or an AI agent, is [/docs/bot](https://telos.alcor.exchange/api/bridge/docs/bot).

How the bridge works:

* **Telos holds the ledger**, `bridge.alcor`. Every route runs between Telos and one other chain. Two other chains are joined by the `hop.alcor` contract on Telos.
* **A deposit** is locked in the vault on its chain, proved on Telos by the bridge's relayer and paid to the recipient there. You send one transaction.
* **A withdrawal** is burned on Telos and proved on the destination chain. Into WAX, XPR and Vaulta the relayer pays it out. Into an EVM chain, Sui, NEAR or TON someone sends the proof there: the recipient, or our courier when the withdrawal pays it a small fee.
* **Keys** name each leg: `d:<domain>:<nonce>` for a deposit, `w:<id>` for a withdrawal. Every endpoint of the [Bridge API](#bridge-api) takes them.

<Callout type="warn">

Do not hardcode addresses in a bot. Read them from <code>GET /v1/chains</code> (<code>sources[].contracts</code>) and <code>GET /v1/routes</code> (<code>how</code>). They are listed below for orientation, as of 2026-11-21.

</Callout>

### Domains and units

| Chain | Domain |
| --- | --- |
| Ethereum | `1` |
| BSC | `56` |
| Polygon | `137` |
| WAX | `1181148696416462999` |
| XPR Network | `4057084141687023600` |
| Vaulta | `12439917377594391589` |
| Sui | `3856007665771390095` |
| NEAR | `14338890689662875897` |
| TON | `1703391080095596199` |
| Solana | `4983630567019438759` |

The domain names the far chain in every memo and key: an EVM chain id, or for
the others the first 8 bytes of the chain's id. It is a decimal string in the
API: most are larger than a JSON number holds exactly.

**Amounts.** The ledger counts in Telos units (the token's precision on Telos).
On an EVM chain `amount = canonical × scale`: `scale` is `1` for USDC and USDT
and `10^10` for ETH, BNB and POL (18 decimals there, 8 on Telos). A remainder
below `scale` is not taken.

**Telos accounts on EVM.** `telosTo` is an Antelope account name packed into a
`uint64`, the standard Antelope encoding. With
[wharfkit](https://wharfkit.com): `BigInt(Name.from('hop.alcor').value.toString())`.

### Deposit from an EVM chain

```javascript
import { Contract, toUtf8Bytes, hexlify } from 'ethers'   // ethers v6
import { Name } from '@wharfkit/antelope'

const API = 'https://telos.alcor.exchange/api/bridge/v1'
const vaultAbi = [
  'function deposit(address token, uint256 amount, uint64 telosTo, address refundTo, uint64 fillFee, uint64 filler, bytes memo)',
  'function depositNative(uint64 telosTo, address refundTo, uint64 fillFee, uint64 filler, bytes memo) payable',
]

const { sources } = await (await fetch(`${API}/chains`)).json()
const vault = new Contract(sources.find(s => s.id === 'mainnet').contracts.vault, vaultAbi, signer)

const telosName = n => BigInt(Name.from(n).value.toString())
const me = await signer.getAddress()

// ETH to the WAX account alice.wam, back to me if WAX never pays
const memo = hexlify(toUtf8Bytes(`1181148696416462999:alice.wam|1:${me}`))
await vault.depositNative(telosName('hop.alcor'), me, 0, 0, memo, { value: 10n ** 16n })

// 50 USDC to the Telos account alice (approve the vault first)
const USDC = '0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48'
await vault.deposit(USDC, 50_000000n, telosName('alice'), me, 0, 0, '0x')
```

| Parameter | Type | Description |
| --- | --- | --- |
| token | address | ERC-20 address from [Routes](#bridge-api) (`how.deposit.token`) |
| amount | uint256 | Raw token units |
| telosTo | uint64 | Who receives on Telos: an account, or `hop.alcor` to go on to another chain |
| refundTo | address | Where the deposit goes back if it cannot be delivered. Must not be zero |
| fillFee, filler | uint64 | Reserved. Pass `0` |
| memo | bytes | Up to 256 bytes, see below |

**Where it lands** depends on `telosTo` and `memo`:

* **A Telos account, no memo**: paid to it on Telos, nothing to collect.
* **A Telos account or contract, with a memo**: delivered to it as a `wrap.alcor` transfer carrying that memo. This is how a deposit pays a contract.
* **Another chain**: `telosTo = hop.alcor`, memo `<domain>:<recipient>|<this chain's domain>:<your address>` — where it goes, then where it comes back if it is never paid there. On WAX, XPR and Vaulta the tokens arrive by themselves; check first that the account exists.

USDT on Ethereum refuses to change a non-zero allowance: set it to `0` first.
A refused deposit reverts with a custom error: `DepositsPaused`,
`AssetDisabled`, `BelowMinimum(minDeposit)`, `CapExceeded`, `AmountTooSmall`,
`MemoTooLong`, `ZeroAccount`, `ZeroRefundAddress`, `UseDepositNative`. The
`Deposit` event gives the key: `d:<chainId>:<nonce>`.

Deposits from Sui, NEAR and TON are one call from the user's wallet there; each
is in [/docs](https://telos.alcor.exchange/api/bridge/docs).

### Deposit from WAX, XPR or Vaulta

```shell
# 100 USDC from WAX to the Telos account alice
cleos -u https://wax.greymass.com push action wrap.alcor transfer \
  '["bob.wam", "bridge.alcor", "100.000000 USDC", "alice"]' -p bob.wam

# 100 USDC from WAX to an address on BNB Smart Chain, delivered by the courier
cleos -u https://wax.greymass.com push action wrap.alcor transfer \
  '["bob.wam", "bridge.alcor", "100.000000 USDC", "hop.alcor:56:0x285202c8db763db06ab42e0705104cb7919ef95e:<fee>|1181148696416462999:bob.wam"]' -p bob.wam
```

A plain transfer to `bridge.alcor` on that chain. The token is the route's
`antelopeToken` in `GET /v1/chains`. The memo says where it goes:

* `<telos account>`: paid to it on Telos.
* `<telos account>:<note>`: delivered to that account as a transfer with `<note>` as its memo.
* `hop.alcor:<domain>:<recipient>[:<fee>]|<this chain's domain>:<your account>`: on to another chain. With `<fee>` — the `withdrawal` of `GET /v1/fees` for that chain and token — our courier delivers it on an EVM chain, Sui, NEAR or TON; without it the recipient releases it there. The second half is where it comes back if it is never delivered.

### Withdraw from Telos

```shell
# 50 USDT from Telos to an Ethereum address
cleos -u https://mainnet.telos.net push action wrap.alcor transfer \
  '["alice", "bridge.alcor", "50.000000 USDT", "1:0x285202c8db763db06ab42e0705104cb7919ef95e"]' -p alice

# 10 WAX from Telos to the WAX account bob.wam
cleos -u https://mainnet.telos.net push action wrap.alcor transfer \
  '["alice", "bridge.alcor", "10.00000000 WAX", "1181148696416462999:bob.wam"]' -p alice
```

A transfer of a `wrap.alcor` token to `bridge.alcor` on Telos, with the
destination in the memo: `<domain>:<recipient>[:<fee>[:<memo>]]`.

* **Into WAX, XPR or Vaulta** the relayer pays it out in about two minutes. A memo after a fee of `0` — an exchange's deposit memo — is the payout's memo.
* **Into an EVM chain, Sui, NEAR or TON** with a `fee` from `GET /v1/fees` our courier delivers it; without one it waits for the recipient to release it there (next section). To NEAR the memo field is the account id; to TON it is sent as a comment.
* The amount must not exceed `withdrawableNow` of the route in `GET /v1/chains`: each vault lets only so much out per day.

The withdrawal id is in the inline `bridge.alcor::wdlog` action of your
transaction. The key is `w:<id>`.

### Release on an EVM chain

```javascript
import { Contract } from 'ethers'

const withdrawalsAbi = [
  'function release((uint64 id, uint64 domain, address token, address recipient, uint64 amount, uint64 deadline, uint64 fee, bytes memo, uint64 recvSequence, bytes32 witness, bytes32[] actionSiblings, uint256 actionPath, bytes32 actionMroot, uint32 majorVersion, uint32 minorVersion, uint32 blockNum, uint32 timestamp, uint32 parentTimestamp, bytes32 finalityDigest, bytes32[] treeSiblings, uint256 treePath, bytes32 finalityMroot) p)',
  'function submitAndRelease((uint32 majorVersion, uint32 minorVersion, uint32 activeGeneration, uint32 lastPendingGeneration, bytes32 finalityMroot, bytes32 lastPendingPolicyDigest, uint32 lastPendingPolicyStart, bytes32 reversibleBlocksMroot, uint32 qcClaimBlockNum, bytes32 qcClaimFinalityDigest, uint32 qcClaimTimestamp, uint32 timestamp, bytes32 baseDigest) f, bytes bits, bytes signature, bytes32[] policyKeys, (bytes policy, bytes bits, bytes signature) pending, (uint64 id, uint64 domain, address token, address recipient, uint64 amount, uint64 deadline, uint64 fee, bytes memo, uint64 recvSequence, bytes32 witness, bytes32[] actionSiblings, uint256 actionPath, bytes32 actionMroot, uint32 majorVersion, uint32 minorVersion, uint32 blockNum, uint32 timestamp, uint32 parentTimestamp, bytes32 finalityDigest, bytes32[] treeSiblings, uint256 treePath, bytes32 finalityMroot) p)',
]

const p = await (await fetch(`${API}/proofs/w:${id}`)).json()   // 404 until the proof exists

if (p.track === 'light') {
  // a root covering this burn is already trusted: ~145–180k gas
  await new Contract(p.light.releaseTo, withdrawalsAbi, signer).release(p.light.release)
} else {
  // the root is submitted in the same transaction: ~2.6M gas
  const s = p.hard.submitRoot
  await new Contract(p.hard.releaseTo, withdrawalsAbi, signer)
    .submitAndRelease(s.finality, s.bits, s.signature, s.policyKeys, s.pending, p.hard.release)
}
```

Anyone may send the proof: every field is checked against a root signed by
Telos finalizers, and the tokens go only to the recipient the burn named.

1. Wait until `GET /v1/transfers/w:<id>` shows `hasProof: true`, about a minute after the burn.
2. Fetch `GET /v1/proofs/w:<id>` and pass its objects through unchanged.
3. Send `release` on the `light` track or `submitAndRelease` on the `hard` track.

Past the `deadline` (about a week after the burn) `release` reverts with
`PastDeadline`; send the same body to `expire` (or `submitAndExpire`) and the
tokens come back on Telos. A release over the vault's daily allowance reverts
with `OutflowLimited` and works once it refills. A withdrawal's `fee` goes to
whoever sends the release. Release on Sui, NEAR and TON is in
[/docs](https://telos.alcor.exchange/api/bridge/docs).

### Telos actions

| Action | Who may call | What it does |
| --- | --- | --- |
| `bridge.alcor::forward(domain, nonce)` | Anyone | Delivers a deposit that carried a memo. The relayer does it; call it if you do not want to wait |
| `bridge.alcor::bounce(domain, nonce)` | Anyone, an hour after arrival | Sends an undeliverable deposit back to its `refundTo` |
| `bridge.alcor::claim(owner, sym_code)` | The owner | Collects what waits in the `claims` table for an account. Rare: deposits are paid out directly |
| `hop.alcor::recover(id)` | Anyone | Sends a hop that came back from its destination on to its way-back address |
| `<gateway>::credit` | Anyone, with a proof | Credits a deposit. The relayer does it. To do it yourself, send the `actions` of `GET /v1/proofs/d:<domain>:<nonce>` in one transaction |

### Contract events

| Contract | Event | Meaning |
| --- | --- | --- |
| `AlcorVault` | `Deposit(token, from, amount, canonical, telosTo, nonce, refundTo, fillFee, filler, memo)` | Deposit locked. Key `d:<chainId>:<nonce>` |
| `AlcorVault` | `Released(id, token, to, amount, feeTo, fee)` | Withdrawal `w:<id>` paid out, raw units |
| `AlcorVault` | `Voided(id)` | Withdrawal `w:<id>` expired, refunded on Telos |
| `AlcorWithdrawals` | `Released(id, token, to, amount, memo)` | The same payout with the Telos memo, in Telos units |
| WAX, XPR, Vaulta `bridge.alcor` | action `deplog(…)` | Deposit from that chain. Key `d:<domain>:<nonce>` |
| Telos `bridge.alcor` | action `wdlog(id, domain, vault, token, recipient, amount, deadline, fee, memo)` | Withdrawal opened. Key `w:<id>` |
